## 문제

맛집 서비스 뽈레에는 사용자가 올린 식당 사진이 백만 장 규모로 쌓여 있었고, 식당마다 대표 사진을 고르는 일은 운영팀의 수작업이었다. 사진의 좋고 나쁨은 화질이 아니라 담음새와 구도 같은 도메인 기준으로 정해졌기 때문에, 범용 화질 지표를 그대로 쓸 수 없었다. 모델을 만들기 전에 기준을 정하고 라벨을 만드는 일부터 시작해야 했다.

## 결과

같은 라벨과 학습 설정에서 비교한 백본별 baseline은 아래와 같다. 전체 오차만 보면 ConvNeXt-Base(384)가 가장 낮았지만, 1점과 5점 구간까지 고려하면 ConvNeXt V2-Base(384)가 가장 경쟁력 있었다.

| 백본 | MAE | RMSE |
| --- | ---: | ---: |
| efficientnet_b0 | 0.629 | 0.813 |
| efficientnet_b2 | 0.587 | 0.790 |
| convnext_tiny | 0.551 | 0.725 |
| convnext_small | 0.543 | 0.727 |
| convnextv2_base_384 | 0.530 | 0.706 |
| convnext_base_384 | 0.527 | 0.696 |

최종 모델은 ConvNeXt V2-Base(384) + weighted MSE다. 추론 클래스는 학습과 같은 전처리로 이미지 한 장의 점수를 돌려주고, Ruby 웹 서버가 PyCall로 이 클래스를 임포트해 프로세스 시작 시 모델을 상시 로드하도록 연동했다. 안정화 이후에는 이미지를 전수 평가한 뒤 상위 후보만 사람이 검수하는 구조로 바꿨다.

## 한계와 다음 단계

- 학습 데이터가 한식에 치우쳐 있어 양식·카페처럼 적게 본 업종의 평가는 약하다. 업종별 데이터를 늘리는 것이 다음 과제다.
- 4~5점 라벨의 절대 수가 적다. 손실 가중치는 완화책이지 해결책이 아니며, 클래스별 최소 수백 장 확보가 필요하다.
- 운영 전후의 검수 시간과 배포 모델의 성능 수치는 측정 조건을 확인한 뒤에 싣는다. 재검수 루프와 어드민 코드는 회사 저장소에 있다.
